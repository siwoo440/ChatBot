# 서버 토큰 지갑 연결과 검증

2단계 구현은 로컬 검증을 완료한 뒤 사용할 연결 코드다. 현재 기본 설정은 연습용이며 실제 원격 프로젝트·실제 계정·두 컴퓨터 간 지갑 확인은 아직 하지 않았다.

---
## 1. 준비와 활성화

1. `docs/ACCOUNT-SETUP.md`의 실제 계정 설정과 `supabase/account-setup.sql` 적용을 먼저 확인한다.
2. 같은 프로젝트의 SQL Editor에서 `supabase/wallet-setup.sql`을 실행한다. 기존 저장본과 연습 잔액을 지우거나 실제 지갑으로 옮기지 않는다. 재실행해도 지갑과 원장은 보존한다.
3. `.env.local`의 공개 계정 설정은 기존처럼 유지한다. 서버 전용 `SUPABASE_SECRET_KEY`에는 해당 프로젝트의 Secret key 또는 예전 service_role 키를 넣는다. 파일 내용을 대화·로그·커밋으로 출력하지 않는다. `NEXT_PUBLIC_`로 시작하는 변수에 비밀 키를 넣지 않는다.
4. `SERVER_WALLET_ENABLED=true`로 설정하고 다시 빌드·실행한다. 공개 실제 AI 스위치는 계속 끈다. 키를 준비하는 것만으로 실제 AI를 호출하지 않는다.
5. 시험 계정으로 로그인해 `/settings/tokens`의 「서버 계정 지갑」과 `/rewards`의 출석을 확인한다. 원격 SQL 권한은 해당 프로젝트에서 별도로 확인해야 한다.

실제 계정은 잔액 0부터 시작한다. 연습용 1,240토큰, 백업 파일의 잔액, 로컬 미션 진행은 실제 토큰으로 바뀌지 않는다. 출석은 기존 정책인 1~6일차 5토큰, 7일차 20토큰이다. 결제·유료 토큰 지급 기능은 연결하지 않았다.

---
## 2. 권한과 요청 처리

- `mv_wallets`: 잔액·누적 사용·출석·요청 한도. `mv_wallet_entries`: 지급·차감·반환 원장. `mv_wallet_requests`: 요청 UUID·내용 지문·예약 상태·사용 당시 채팅 정보. `mv_wallet_usage`: 한국 날짜별 전체 한도.
- 모든 표에 RLS 적용. 로그인 사용자는 본인 지갑·원장만 읽는다. 익명 요청의 조회와 브라우저의 변경·RPC 실행은 차단한다.
- `mv_wallet_command`와 보조 함수는 `SECURITY INVOKER`, 빈 `search_path`, 서비스 역할에만 실행 권한을 부여한다. 서버는 매 요청마다 사용자 JWT를 확인하며 브라우저가 보낸 사용자 ID·보상량·잔액은 받지 않는다.
- 서버는 검증한 등급·길이·유저 노트로 비용을 계산하고, 같은 계정의 지갑 행을 잠근 상태에서 잔액 확인과 차감을 처리한다. 요청 번호가 같으면 실제 AI를 다시 호출하지 않으며, 같은 번호에 다른 내용을 붙이면 거절한다.
- 요청 번호는 `x-wallet-request-id` UUID, 채팅 표시 정보는 요청 본문의 `wallet`이다. 채팅 제목·캐릭터·버전은 표시용 정보이며 인증 근거로 사용하지 않는다.
- `GET /api/wallet`은 본인 상태만 반환한다. `POST /api/wallet`은 허용한 보상 이름만 받는다. 서버 비밀 키는 RPC의 서버 연결에서만 사용한다.

---
## 3. 차감·반환·사용량 기준

1. 실제 호출 전 예약 차감. 첫 유효 응답을 얻은 뒤 브라우저로 보내기 직전에 사용 확정.
2. 확정 전 오류·빈 답변·중단은 반환. 응답 확정 후 오류·중단은 사용 유지. 재시도·다시 생성·수정 후 응답은 각각 새로운 요청. 연습 AI 응답은 실제 계정 토큰을 차감하지 않음.
3. 프로세스 중단·DB 통신 장애로 반환을 확인하지 못한 미확정 예약은 10분이 지난 뒤 다음 지갑 조회나 요청에서 반환. 사용 확정이 이미 DB에 반영된 요청은 반환하지 않음. 네트워크가 끊긴 경우 이용 내역으로 최종 상태 확인.
4. 실제 AI 답변은 2분 제한. 분·일·서비스 전체 한도는 DB에 저장하며 서버 재시작으로 초기화되지 않음. 하루는 한국 자정 기준. 실패·반환한 요청도 호출 횟수 한도에는 포함.
5. 보조 AI는 당일 완료 대화당 최대 두 번(스탯·요약 용도). 전체 일일 한도를 정했다면 보조 요청도 그 두 배까지 제한. 보조 요청 한도 초과 시 기존 연습 규칙으로 보조 결과 처리.
6. 기본 한도는 사용자 분당 20요청·하루 300대화. 서비스 전체 한도는 기본 미설정이며 공개 전에 운영 예산에 맞춰 `CHAT_TOTAL_MESSAGES_PER_DAY`를 정해야 함. 가격·결제 정책은 미확정.

## 4. 이용 내역과 보상 범위

`/settings/tokens`에 한국 시간의 연·월·일·시·분·초, 사용 당시 채팅방 이름, 작품, 비용, 잔액과 이동 링크를 표시한다. 채팅방 이름을 바꿔도 당시 이름을 남긴다. 삭제한 채팅방은 기록만 보존하고 연결하지 않는다. 옛 기록에 식별자가 없으면 추측으로 연결하지 않는다.

서버 원장은 계정에 계속 저장하고 화면에는 최근 300건을 제공한다. 기간 합계와 그래프는 표시 대상 기록의 합계이며 전체 원장의 무제한 검색은 제공하지 않는다. 반환은 별도 지급 방향 거래로 표시하므로 원래 사용과 반환이 모두 보이고, 지갑 누적 사용은 반환을 제외한다. 대화 내용 자체는 원장에 넣지 않고 표시 정보와 요청 지문을 저장한다.

실제 보상은 출석, 당일 메시지 5회·새 대화 1회, 주간 메시지 30회·새 대화 3회·출석 5일을 서버 실적으로 검증한다. 좋아요·모두 완료·초대 보상과 실제 이미지 생성은 검증 가능한 서버 데이터가 생긴 뒤 연결한다. 브라우저 데이터 초기화·JSON 가져오기·서버 저장본 교체는 실제 지갑을 초기화하지 않는다. 계정 탈퇴 시 지갑·원장도 외래 키 규칙으로 함께 삭제된다.

---
## 5. 검증 명령과 남은 확인

`npm run test:wallet-db`는 고정 버전 PGlite에서 배포 SQL 자체를 실행한다. 외부 프로젝트·실제 AI·실제 계정을 사용하지 않는다. 직접 변경 권한, 본인 원장 격리, 중복 요청·반환, 부족한 잔액, 경합 요청, 미확정 예약 회수, 출석·미션, 날짜 경계, 파일 저장소 재시작과 설치 재실행을 검사한다.

PGlite는 단일 연결로 요청을 직렬 처리한다. 동시에 보낸 요청의 잔액 보호는 검사하지만 실제 PostgreSQL의 여러 연결 사이 잠금 경합을 재현한 것은 아니다. 원격 환경에서 아래 항목을 추가 확인해야 한다.

| 항목 | 상태 |
| --- | --- |
| 원격 SQL 적용·DB 권한 검사 | 미확인 |
| 실제 계정 A/B의 지갑·원장 분리 | 미확인 |
| 두 물리 컴퓨터의 잔액·내역 일치 | 미확인 |
| 여러 DB 연결의 동시 차감·같은 요청 재전송 | 미확인 |
| 실제 모델의 첫 조각 전·후 실패와 반환 | 미확인 |
| 공개 한도·예산·데이터 보관 정책 확정 | 미확정 |
